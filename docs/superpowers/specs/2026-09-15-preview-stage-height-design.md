# 미리보기 스테이지 높이 (2026-09-15)

## 문제

멀티 슬라이드 미리보기(업로드 PPTX 덱)가 `max-height: 600px` 안에서 스크롤한다.
이 캡은 미리보기가 설정 폼 **아래**에 붙어 있던 시절의 규칙이다. 그때는 미리보기가
페이지를 무한히 밀어내지 않도록 막아야 했다.

3단 워크스페이스 리팩토 이후 스테이지는 독립된 열이 되었는데, 미리보기만 600px에
갇혀서 남는 세로 공간을 버리고 상자 안에서 또 스크롤한다. 덱이 길면 바깥 페이지까지
같이 움직이므로 같은 방향으로 도는 스크롤이 두 겹이 된다.

## 측정에서 드러난 진짜 원인

600px 캡만 걷어내고 재보니 페이지 스크롤이 199px 남았다. 스테이지 위에 크롬이
**300px** 쌓여 있었다.

| 구간 | 높이 |
| --- | --- |
| 페이지 상단 패딩 | 48px |
| 전역 헤더·네비 | 93px |
| PPT 탭바 | 43px |
| 갭 + 패널 패딩 + 에디터 헤더 | 116px |
| **스테이지 시작** | **300px** |
| 아래 (패널 패딩 24 + 페이지 패딩 64) | 88px |

이 상태로 페이지 스크롤을 0으로 만들려면 스테이지가 `100vh - 388px`이 되는데,
1000px 화면에서 581px으로 **지금의 600px보다 작아진다**. 즉 캡은 증상이었고,
크롬 예산이 원인이었다.

## 설계

### 슬라이드 에디터를 문서가 아니라 앱 화면으로 다룬다

이 앱의 다른 화면은 위에서 아래로 읽는 문서다. 슬라이드 에디터는 아니다. 오른쪽에서
설정을 바꾸고 왼쪽에서 결과를 보는 화면이므로 두 패널이 동시에 보여야 한다. 그 아래로
페이지가 따로 스크롤하면 같은 방향 스크롤이 두 개가 되고, 패널이 쓸 수 있었던 높이가
버려진다.

그래서 `.page[data-ppt-surface="editor"]`가 뷰포트 하나를 정확히 차지하고, 늘어날 수
있는 영역(슬라이드 레일, 스테이지, 인스펙터)이 각자 자기 상자 안에서 스크롤한다.
`data-ppt-surface`는 `workspace-layout.js`가 이미 `.page`에 쓰고 있던 속성이며,
이 규칙이 첫 소비자다.

각 단계마다 `minmax(0, ...)`와 `min-height: 0`이 필요하다. 그리드/플렉스 아이템의
기본값 `min-height: auto`는 콘텐츠보다 작아지기를 거부해서, 넘친 높이를 다시 페이지
바깥으로 밀어낸다.

### 크롬 다이어트

에디터 화면에서는 세로가 희소 자원이므로 읽기 중심인 성경 텍스트 화면보다 좁게 쓴다.
페이지 패딩 48/64 → 24/16, `.page` 갭 32 → 16, 탭바 아래 여백 24 → 16.
스테이지 시작이 300px → **252px**로 내려왔다.

### 높이 토큰의 두 가지 모드

`--stage-max-h`를 `.slide-editor-panel`에 두고 인스펙터와 스테이지가 공유한다.

- **문서 모드(900px 미만):** `calc(100vh - 190px)`. 패널이 세로로 쌓이면 자기 자신이
  뷰포트 어디에 있는지 알 수 없으므로 보수적인 캡 하나를 나눠 쓴다.
- **앱 셸 모드(900px 이상):** `none`. 실제 남은 높이가 셸에서 내려오므로 캡이
  비켜서야 한다.

토큰 값만 바꾸면 `.editor-form`과 `.preview-area` 양쪽이 따라오므로, 속성별로
`max-height`를 덮어쓰는 규칙을 따로 둘 필요가 없다.

### 캡을 상자가 아니라 스테이지 영역에 건다

문서 모드에서 상자에 직접 캡을 주면 `미리보기` 레이블과 gap만큼(약 31px) 인스펙터보다
아래로 내려간다. 그래서 스크롤 모드일 때 영역 전체를 클램프한다:

```css
.preview-area:has(.preview-scroll-mode) {
  max-height: var(--stage-max-h);
  grid-template-rows: auto minmax(0, 1fr);
}
```

`minmax(0, 1fr)`의 `0`이 핵심이다. 기본값 `auto`면 행이 덱 전체 높이 아래로 줄지 못해
`overflow-y: auto`가 발동하지 않는다.

### 단일 슬라이드 16:9는 건드리지 않는다

스테이지를 `align-self: stretch`로 늘리되 `.preview-area`에 `align-content: start`를
준다. 이게 없으면 늘어난 행이 상자 높이를 덮어써서 `aspect-ratio: 16/9`가 깨진다.
스크롤 모드에서는 `1fr` 행이 여유 공간을 먼저 흡수하므로 `align-content`가 나눠 줄
공간이 남지 않아 영향이 없다.

### 컴팩트 모드 드로어

900–1279px에서 슬라이드 목록과 인스펙터는 패널 위에 떠 있는 드로어다. 뷰포트 기준
`calc(100vh - 190px)`을 유지하면 위쪽 크롬만큼 넘쳐서 페이지 스크롤을 되살린다.
셸에서는 패널이 이미 정확히 뷰포트 높이이므로 패널 기준(`100%`, `calc(100% - 88px)`)
으로 잰다.

## 결과 (측정값)

미리보기 상자 높이, 괄호는 페이지 스크롤 잔량.

| 뷰포트 | 이전 | 이후 |
| --- | --- | --- |
| 1500×1000 | 600px (199px) | **676px (0)** |
| 1500×870 | 600px (199px) | 546px (0) |
| 1500×800 | 600px (199px) | 476px (0) |
| 1100×900 (컴팩트) | 600px (199px) | 576px (0) |
| 860×900 (모바일) | 600px | 679px (문서 모드 유지) |

짧은 화면에서는 상자가 전보다 작아지지만 전체가 한 화면에 들어온다. 600px짜리 상자를
보려고 페이지를 먼저 스크롤하던 것보다 낫다는 판단이다.

## 영향 범위

- 뷰어는 `scrollContainer: slidePreview`로 같은 엘리먼트를 계속 쓴다. 컨테이너가
  높아지면 lazy 윈도우가 한 번에 더 많은 장을 올린다 — 설정 변경 없이 따라온다.
- 뷰어는 폭으로 맞추므로 높이 변화만으로 refit이 필요 없다.
- `#view-ppt`는 인라인 `display: grid` → `flex`로 바꿨다. 탭바 위 바들이 상황에 따라
  나타났다 사라지므로, 마지막 자식이 남은 높이를 가져가는 열 플렉스가 맞다.
- 줌 오버레이(`position: absolute`)와 파일명 배지(`position: sticky; bottom`)는
  상자가 높아져도 그대로 동작한다.
- 성경 텍스트 화면과 템플릿 갤러리는 `data-ppt-surface`가 `editor`가 아니므로
  문서 스크롤 그대로다.

## 비목표

필름스트립, 페이지 점, "한 장씩 보기" 토글. 세로 스택 자체는 찬송·업로드 덱 검수에
맞으므로 유지한다.

## 검증

`tmp-preview-height-check.mjs`(임시)로 합성 덱을 넣고 5개 뷰포트에서 측정했다:
상자 높이, 상자 내부 스크롤 발생, 인스펙터와 바닥 정렬, 페이지 스크롤 잔량,
스크롤 모드 해제 후 16:9 복귀. 스크린샷으로 단일 슬라이드·덱·커스텀 캔버스·포커스
모드·컴팩트 드로어·갤러리·추출기 화면을 확인했다.
